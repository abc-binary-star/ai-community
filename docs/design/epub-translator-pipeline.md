# EPUB 翻译流水线解耦分析

> 从一本外文 EPUB 到一本简体中文 EPUB：全流程步骤拆解、职责归属（AI / 人工 / 规则引擎）与解耦设计。
> 适用服务：`apps/epub-translator`

## 1. 总览

整条流水线可拆为 **10 个阶段**。每个阶段产出**中间产物（Artifact）**，阶段之间只依赖产物契约、互不依赖实现——这是解耦的核心。人机协作遵循一个原则：

> **AI 负责"量大、确定性强、可迭代"的工作；人负责"影响全局、不可逆、主观判断"的决策。**

```
┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
│1 文件接入│ → │2 结构解析│ → │3 术语抽取│ → │4 智能分块│ → │5 AI翻译 │
│ 纯自动  │   │ 纯自动  │   │ AI+人  │   │ 纯自动  │   │ AI+审校 │
└────────┘   └────────┘   └────────┘   └────────┘   └────────┘
                                              │
                                              ▼
┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
│10 社区发布│ ← │9 导出发布│ ← │8 质量QA │ ← │7 格式组装│ ← │6 一致性 │
│ 人+社区  │   │ 纯自动  │   │ AI+人  │   │ 纯自动  │   │ AI+人  │
└────────┘   └────────┘   └────────┘   └────────┘   └────────┘
```

## 2. 阶段明细

### 阶段 1 · 文件接入与格式校验

| 项 | 内容 |
|---|---|
| **子步骤** | 上传 → ZIP 完整性校验 → mimetype/container.xml 校验 → EPUB 2/3 版本识别 → OPF/NCX 元数据解析（书名/作者/语言/目录/spine）→ 源语言检测（元数据 + 文本抽样）→ DRM/加密检测 |
| **负责方** | 规则引擎（全自动，零 AI） |
| **人工介入** | 无。仅在异常时阻断：加密/DRM 文件、zip 损坏、扫描版（无文本层）提示用户更换 |
| **产物** | `ValidatedBook`（元数据 + spine + 文件清单） |
| **解耦要点** | 后续阶段只消费 `ValidatedBook`，不接触原始 zip |

### 阶段 2 · 内容结构解析

| 项 | 内容 |
|---|---|
| **子步骤** | 按 spine 拆章节 → 遍历 XHTML 提取可翻译文本节点（`p/h1-6/li/td/blockquote`…）→ 识别非文本元素（图片/代码块/公式/表格/旁注）→ 识别特殊文体（对话、诗歌、引用、脚注/尾注锚点） |
| **负责方** | 规则引擎为主 + AI 辅助识别复杂结构（可选：让 LLM 判定某段是否为诗歌/歌词，保持押韵结构） |
| **人工介入** | 无需常规介入。结构标注异常（大量未识别元素）时提示 |
| **产物** | `BookModel`（章节 → 文本块索引，含块类型 `paragraph/heading/poem/quote`） |
| **解耦要点** | 块类型标签是下游 Prompt 的关键输入（诗歌块用"保留韵律"策略） |

### 阶段 3 · 术语抽取与术语表确认 ⭐ 首个关键人工关卡

| 项 | 内容 |
|---|---|
| **子步骤** | AI 通读全书抽取专有名词（人名/地名/机构/品牌/专业术语/技术名词）→ 生成候选译名（音译/意译/保留原文）→ 汇总为 `GlossaryDraft` |
| **负责方** | AI 生成草稿 + **人工确认** |
| **人工介入** | **强烈建议**。术语一致性是全书翻译质量的地基，一处定错满书皆错。人审阅草稿：改译名、删误抽、补充自定义术语 |
| **产物** | `Glossary`（已确认术语表） |
| **解耦要点** | 术语表一旦确认即为只读契约，注入后续**所有**翻译与审校 Prompt；支持导入导出（JSON/CSV），可复用同一作者系列书 |
| **扩展** | 术语表可存社区知识库（L2 knowledge），跨书共享 |

### 阶段 4 · 智能分块与上下文管理

| 项 | 内容 |
|---|---|
| **子步骤** | 按章节 + Token 预算（默认 1500）聚合文本块 → 块间设置滑动窗口（前 300/后 100 字符）→ 建立章节摘要链（每章翻译完生成摘要，累积为上下文）→ 维护全局情节摘要 |
| **负责方** | 规则引擎（纯自动，算法固定、结果可复现） |
| **人工介入** | 无 |
| **产物** | `ChunkPlan`（块列表 + 块序号 + 上下文引用 + 进度预算） |
| **解耦要点** | 块序号是后续写回阶段的"寻址键"；分块策略可独立调参（块大小/重叠度）不影响其他阶段 |

### 阶段 5 · AI 分块翻译与自审 ⭐ 核心 AI 环节

| 项 | 内容 |
|---|---|
| **子步骤** | 逐块翻译：注入 `[术语表 + 前文摘要 + 上下文窗口 + 块类型策略]` → LLM 输出译块（**强制保留 HTML 标签**）→ 自审循环：译后校验（术语命中、标签完整性、漏译检测）→ 不合格自动重译（≤N 次） |
| **负责方** | AI Agent（Eino Graph 编排：Translate → Review → 分支重译） |
| **人工介入** | 常规无。**可配置抽检**：用户在 UI 标记"重点关注章节"，该章节块强制多轮审校 |
| **产物** | `TranslatedChunk[]`（含审校记录、Token 用量、置信度） |
| **解耦要点** | 每块独立可重跑（幂等），失败块记录 `RETRYABLE`，支持断点续译 |

### 阶段 6 · 全文一致性校验 ⭐ 关键人工关卡

| 项 | 内容 |
|---|---|
| **子步骤** | 全文扫描：同一人名/术语在全书译名是否统一 → 同一角色跨章节称呼是否一致 → 数字/日期/单位格式规范 → 引语与原文对应 |
| **负责方** | AI 生成 `ConsistencyReport`（列出所有疑似不一致 + 位置 + 建议修正）|
| **人工介入** | 人审阅报告：一键接受全部建议 / 逐条处理 / 忽略。处理结果驱动局部重译（只重译受影响的块，不动全书）|
| **产物** | `ConsistencyReport` → `PatchList`（待重译块清单）|
| **解耦要点** | 报告驱动补丁式重译，避免全书重跑，成本可控 |

### 阶段 7 · 格式还原与组装

| 项 | 内容 |
|---|---|
| **子步骤** | 按块序号将译块**写回原 XHTML**（DOM 级替换，只动 `<body>` 内文本节点，`<?xml?>`/DOCTYPE/head 原样保留）→ 目录/章节标题翻译 → OPF 元数据更新（书名加"（简体中文版）"）→ 图片/字体/CSS 原样保留 |
| **负责方** | 规则引擎（纯自动，确定性逻辑） |
| **人工介入** | 无 |
| **产物** | `DraftEPUB` |
| **解耦要点** | 写回键=块序号（来自阶段 4）；本阶段不依赖任何 AI，纯函数式转换 |

### 阶段 8 · 质量 QA 与人工验收 ⭐ 最终质量关卡

| 项 | 内容 |
|---|---|
| **子步骤** | **结构校验**：epubcheck 格式合规 → **AI 质量评估**：随机/分层抽样评分（忠实度/流畅度/术语一致性，1-5 分）→ 生成 `QAReport` |
| **负责方** | 规则引擎（结构校验）+ AI（质量评估）+ **人工验收** |
| **人工介入** | **发布前必须人工确认**：人可（a）直接验收发布；（b）标记不满意的抽样块进入阶段 6 重译；（c）亲自改稿后回注 |
| **产物** | `QAReport` + 验收结论 |
| **解耦要点** | 验收是"发布门槛"（Gate），不通过则回退到阶段 6，形成闭环 |

### 阶段 9 · 导出与发布

| 项 | 内容 |
|---|---|
| **子步骤** | 生成最终 EPUB → 版本号管理（v1/v2…）→ 源文件与译稿归档 → 提供下载 |
| **负责方** | 规则引擎（纯自动） |
| **人工介入** | 无 |
| **产物** | `FinalEPUB` |

### 阶段 10 · 社区分享与协作（社区生态扩展）

| 项 | 内容 |
|---|---|
| **子步骤** | 发布到社区"实用工具分区" → 邀请他人试读/校对 → 收集勘误 → 生成修订版（回到阶段 6） |
| **负责方** | 人 + 社区协作 |
| **人工介入** | 社区校对是**分布式人工审核**：多人校对报告合并，驱动下一版本迭代 |
| **解耦要点** | 每个发布版本 = 一次独立流水线实例，版本间共享 Glossary 与 QA 基线 |

## 4. 解耦设计原则

1. **Artifact 驱动**：每个阶段只读上一阶段产物、只写本阶段产物。产物是**不可变快照**（版本化），任何阶段失败可从中断点重跑，无需从头。
2. **人机两态并存**：每个有人工关卡的阶段同时提供"AI 自动模式"与"人工确认模式"。自动模式（信任 AI）适合内部自用；确认模式（人把关）适合对外发布。默认推荐**半自动**：术语表确认 + QA 验收强制，其余自动。
3. **补丁式重译**：阶段 6/8 发现的问题只重译受影响块（按块寻址），不触发全量重跑，控制成本。
4. **契约先于实现**：`Glossary`、`ChunkPlan`、`TranslatedChunk`、`QAReport` 的结构定义先固定，各阶段可独立开发、独立测试、独立替换（比如把豆包模型换成其他模型，只影响阶段 5）。
5. **人工成本聚焦**：全部流水线中，人工真正必须投入的只有**两处决策**（术语表确认、QA 验收）和**一个可选动作**（一致性报告审阅）——把人的时间花在影响全局的决策上。

## 6. 关键决策点（人把什么关）

| 关卡 | 把关内容 | 决策错误的影响 | 建议频率 |
|------|---------|--------------|---------|
| 术语表确认 | 人名/地名/专业术语译名 | 全局性、贯穿全书，错误极难事后修复 | 每本书一次 |
| 一致性报告 | 跨章节称呼/译名统一 | 局部性，但影响阅读体验 | 每本书一次（大书必做） |
| QA 验收 | 整体质量是否达发布标准 | 最终交付物 | 每本书一次（发布门槛） |
| （可选）抽样精修 | 特殊文体（诗歌/双关/梗） | 艺术性损失 | 由用户按需开启 |
