# AI 接口限制现状与免费/订阅配额方案

> 项目：Commons AI 兴趣社区
> 日期：2026-08-05
> 范围：Go 后端 `server-go` 全部 AI 接口的限制逻辑

---

## 一、现状梳理

### 1.1 AI 功能清单

当前共 9 个 AI 相关接口，统一在 `internal/pkg/ailimit` 中登记为 8 个功能标识：

| 功能 | 接口 | 功能标识 | 说明 |
|---|---|---|---|
| AI 补全 | POST /api/ai/enrich | enrich | 一次生成标题+摘要+标签，支持单项重生成 |
| 标题建议 | POST /api/ai/suggest-title | suggest_title | 生成 3 个标题候选 |
| 全文/选段润色 | POST /api/ai/rewrite | rewrite | 单次调用 |
| 流式润色 | POST /api/ai/rewrite-stream | rewrite | 按 5000 字/片串行调用，一次请求 = N 次模型调用 |
| 摘要生成 | POST /api/ai/summarize | summarize | 一句话摘要 |
| 语音润色 | POST /api/ai/voice-polish | voice_polish | 口语转书面 |
| 语音转文字 | POST /api/ai/transcribe | transcribe | 火山引擎 ASR，不走 LLM 网关 |
| 标签建议 | POST /api/posts/suggest-tags | suggest_tags | 发帖时标签推荐 |
| 讨论摘要 | POST /api/posts/:id/summary | thread_summary | 异步生成讨论要点 |

### 1.2 现有限制规则（全用户统一）

限制器 `internal/pkg/ailimit/limiter.go` 的默认配置（`DefaultConfig`）：

| 功能 | 每用户每分钟 | 每用户每天 |
|---|---:|---:|
| AI 补全 | 10 | 100 |
| 标题建议 | 10 | 100 |
| 润色（含流式） | 10 | 50 |
| 摘要 | 10 | 100 |
| 语音润色 | 5 | 50 |
| 语音转文字 | 5 | 30 |
| 标签建议 | 10 | 100 |
| 讨论摘要 | 3 | 20 |

全局限制：

| 项目 | 数值 | 配置项 |
|---|---:|---|
| 全局最大并发 AI 调用 | 5 | AI_CONCURRENT_LIMIT |
| 全局每日 token 上限 | 2,000,000 | AI_DAILY_TOKEN_LIMIT |
| 管理员 | 全部豁免 | role=admin |

### 1.3 限制机制

- 三层检查：HTTP 中间件 `AILimit` 先快速拒绝；`ai.Chat` 内部 `PreCheckHook` 兜底；并发信号量控制全局并发。
- 每分钟限流：内存滑动窗口，key 为「用户ID:功能」，单实例生效，重启丢失。
- 每日配额：PostgreSQL `ai_user_quota` 按「用户+日期」累计请求次数，重启不丢失。
- 全局 token：`ai_global_quota` 按日期累计，达 2,000,000 后当日全部 AI 请求返回 429。
- 用量审计：每次 `ai.Chat` 结束写入 `ai_usage_log`（模型、token、耗时、成功/失败）。
- 两级缓存：标题/摘要/标签/补全都有内存+DB 缓存，缓存命中不调用模型、不扣配额。
- 配置：功能级配额硬编码在 `DefaultConfig`；并发与全局 token 上限可经环境变量覆盖。

## 二、现状问题与风险

### 2.1 没有免费/订阅分层

用户模型只有 `role`（user/admin），没有任何 plan/订阅字段。所有非管理员用户共用同一套配额，无法通过付费提升权益，也没有升级入口。

### 2.2 语音转文字实际上「不限量」

`transcribe` 不走 `ai.Chat`，而配额扣减只发生在 `ai.Chat` 的 UsageHook 里。中间件虽然检查了 transcribe 配额，但滑动窗口时间戳从未消费、`ai_user_quota` 也从不累计——配置的 5 次/分、30 次/日完全不生效，只要 25MB 文件限制不超就能无限调用，是成本黑洞。

### 2.3 失败请求也扣配额

`RecordUsage` 无论成功失败都会消费滑动窗口并累加请求次数（与代码注释「仅成功调用才消费」矛盾）。上游超时/报错时，用户重试会快速耗尽每日次数。

### 2.4 流式润色按分片扣费，一次请求可抵 8 次

全文 40000 字会被切成最多 8 个 5000 字分片，每个分片都独立调用模型、独立扣一次 rewrite 配额。一次「润色全文」实际消耗 1~8 次日配额；且中间件只在请求开始时检查一次，若剩余次数不足全部分片，会出现「润色到一半报错」。

### 2.5 AI 补全降级时叠加扣费

`enrich` 解析失败会降级为「标题+摘要+标签」三个单项调用，一次用户请求最多消耗 4 次不同功能的配额（enrich + suggest_title + summarize + suggest_tags）。

### 2.6 没有用户级 token 上限，重接口可烧穿全局预算

`ai_user_quota` 虽然记录 total_tokens，但从未被检查。单个用户可以用 50 次全文润色（约数百万 token）先耗尽全局 200 万 token 日预算，导致全体用户当天不可用。

### 2.7 管理员完全豁免，包括全局 token 上限

管理员检查在全局 token 检查之前直接放行，也不受并发限制，存在被内部账号刷爆供应商账单的风险（有审计日志可追，但无预防）。

### 2.8 用户无配额可见性

没有 `GET /api/ai/usage` 之类的接口，前端也不知道剩余次数，用户只能在 429 时看到「已达上限」，体验差且无法引导升级。

### 2.9 其他工程问题

- 内存滑动窗口只对单实例有效，多副本部署时每分钟限流会按实例放大。
- 功能级配额全部硬编码，不支持按环境/按套餐配置。
- `ailimit.AcquireConcurrent` 是死代码，实际并发由 `ai` 包内信号量控制，两套并发逻辑并存易混淆。
- 讨论摘要异步自动刷新也走触发用户的配额，用户可能因帖子评论区自然增长而被扣费。

## 三、新配额方案（建议稿）

### 3.1 分层设计

| 层级 | 定位 | 权益 |
|---|---|---|
| 免费用户 | 体验社区 + 轻量 AI 辅助 | 核心功能可用、次数较低、重功能限篇幅 |
| 订阅用户（Pro） | 高频创作者与深度阅读者 | 高配额、全文润色/长语音全开、优先响应 |
| 管理员 | 内部运营 | 不限量但全量审计、单独预算池告警 |
| 审核员（可选） | 志愿者/内部 | 建议给 Pro 级配额，避免治理工作被限流 |

### 3.2 免费 vs 订阅配额表

| 功能 | 免费用户 | 订阅用户 |
|---|---:|---:|
| AI 补全 | 10 次/日，5 次/分 | 100 次/日，10 次/分 |
| 标题建议 | 20 次/日，5 次/分 | 100 次/日，10 次/分 |
| 摘要生成 | 20 次/日，5 次/分 | 100 次/日，10 次/分 |
| 标签建议 | 20 次/日，5 次/分 | 100 次/日，10 次/分 |
| 润色（含流式） | 10 次/日，5 次/分，单次 ≤ 8000 字 | 100 次/日，10 次/分，单次 ≤ 40000 字 |
| 语音润色 | 15 次/日，5 次/分 | 50 次/日，10 次/分 |
| 语音转文字 | 5 次/日，2 次/分，音频 ≤ 3 分钟 | 30 次/日，5 次/分，音频 ≤ 25MB（约 13 分钟） |
| 讨论摘要（手动触发） | 5 次/日，2 次/分 | 30 次/日，5 次/分 |

个人与全局预算：

| 预算项 | 免费用户 | 订阅用户 |
|---|---:|---:|
| 个人每日 token 预算 | 100,000 | 500,000 |
| 全局每日 token 分池 | 700,000（免费共享） | 1,300,000（订阅共享） |
| 全局并发 | 全局 5；免费 ≤ 2 | 全局 5；订阅 ≤ 4 |
| 缓存命中 | 不计费、不扣次数 | 同左 |

> 说明：以上数字是建议起点，上线前用 `ai_usage_log` 跑一周真实分布再校准。轻功能（标题/摘要/标签）单次约 1~3k token，中功能（补全/语音润色/讨论摘要）约 3~8k token，重功能（全文润色）约 20~100k token。

### 3.3 配额扣减规则（修复现状问题）

1. **语音转文字接入统一计量**：STT 调用完成后同样写审计日志并扣减次数/分钟配额。
2. **失败不扣每日次数与 token**：滑动窗口频率无论如何都消费（防刷）；每日请求次数与 token 仅在成功时扣减。
3. **流式润色按「一次用户请求」扣 1 次**：请求开始时预留配额；每个分片只检查 token 预算，不重复扣次数。token 预算中途耗尽时停止后续分片并明确提示。
4. **AI 补全降级只按 enrich 扣 1 次**：降级调用消耗的 token 计入 enrich 的 token 预算，不再叠加其他功能次数。
5. **缓存命中不扣配额**（保持现状）。
6. **讨论摘要**：手动触发计入用户配额；因新评论导致的异步自动刷新计入系统/管理员池，不扣用户配额。
7. **订阅到期自动降级**：到期后立即按免费配额执行，建议给 3 天宽限期并在前端提示续费。

### 3.4 数据模型与接口改动

数据模型：

```text
users:
  + plan VARCHAR(20) DEFAULT 'free'      -- free / pro
  + plan_expires_at TIMESTAMP NULL       -- 订阅到期时间

subscriptions（新增，便于对账）:
  id, user_id, plan, status, started_at, expires_at,
  provider, provider_order_id

ai_user_quota:
  复用现有 request_count / total_tokens，增加 plan 维度检查

ai_quota_config（或代码配置）:
  plan, feature, per_minute, per_day, daily_token_budget
```

新增接口：

- `GET /api/ai/usage`：返回今日各功能剩余次数、剩余 token、订阅到期时间。
- `GET /api/ai/plan`：返回当前套餐与可升级权益（未订阅时用于引导）。
- `POST /api/billing/upgrade`：本期可先做占位，支付接入后启用。

前端改动：

- 配额不足时按钮置灰并提示「今日免费额度已用完」，附升级入口。
- 429 响应体携带剩余时间与升级链接（`Retry-After` 已有，补充 body 字段）。
- 设置页展示套餐与用量。

### 3.5 配置化

功能级配额从硬编码改为按套餐配置，支持环境变量或配置表覆盖：

```text
AI_FREE_ENRICH_DAY=5
AI_FREE_REWRITE_CHARS=8000
AI_PRO_DAILY_TOKEN=500000
AI_FREE_GLOBAL_TOKEN_POOL=600000
AI_PRO_GLOBAL_TOKEN_POOL=1400000
```

### 3.6 分阶段落地

| 阶段 | 内容 | 工期 |
|---|---|---:|
| P1 计量修复 | 转写计量、失败不扣费、流式按请求扣、补全降级单次扣、用户级 token 上限 | 2~3 天 |
| P2 分层与可见性 | users.plan + 订阅表、按套餐取配置、全局分池、并发分池、usage/plan 接口、前端提示 | 2~3 天 |
| P3 商业化 | 支付接入、到期降级、升级引导、新用户风控、Redis 分布式限流 | 1~2 周 |

### 3.7 待拍板决策

1. Pro 定价与配额数字是否按本方案起步？
2. 免费用户是否开放流式全文润色？建议开放但限制 8000 字。
3. 失败请求不扣次数但扣频率，是否可接受？
4. 全局分池 60 万 / 140 万是否合适？（当前总盘 200 万）
5. 审核员是否给 Pro 级配额？
6. 是否引入新用户风控（注册 3 天内、未绑定手机号者配额减半）？
